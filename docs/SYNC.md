# 同期範囲・保持期間（取得する期間の選択）

**ステータス:** 計画（実装未着手）
**結論:** **すべてを無条件に取り込むのではなく、取得する期間をユーザーが選べる**（アカウント単位）。本文・添付は段階的に取得して軽快さと容量を両立する。

関連: [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md)（Phase 4）/ [CROSS_PLATFORM.md](CROSS_PLATFORM.md)（独立 IMAP 同期）/ [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) / [DATA_STORAGE.md](DATA_STORAGE.md)

---

## 1. 同期ウィンドウ（ユーザー選択）

アカウントごとに「どこまで遡って取り込むか」を選べる。

- 選択肢（例）: **過去 1ヶ月 / 3ヶ月 / 6ヶ月 / 1年 / 2年 / 全期間**
- **既定: 6ヶ月**（軽快さと実用性のバランス。`全期間` はオプトイン）
- 端末ごとに異なる設定でよい（[CROSS_PLATFORM.md](CROSS_PLATFORM.md) の独立 IMAP 同期と整合。各端末が自分のウィンドウで同期）。
- 変更時: ウィンドウを広げたら不足分を追加取得、狭めたら範囲外をローカルから整理（下記 保持ポリシー）。

---

## 2. 段階的取得（メタデータ → 本文 → 添付）

全文を一度に落とさず、必要なものから取得して軽量・高速に保つ。

| レイヤ | 取得方針 |
|---|---|
| **ヘッダ/メタデータ** | 同期ウィンドウ内は取得。スレッド再構築・フィルタ・一覧の基盤（軽い） |
| **本文（clean_body）** | ウィンドウ内は取得（既定）。または開いた時にオンデマンド取得も選択可 |
| **添付ファイル** | **遅延取得**（開いた時／明示ダウンロード時）。サイズ上限・自動DL条件は設定可 |

> これにより「メタデータは広く・本文/添付は必要分だけ」を実現し、初回同期と容量を抑える。

---

## 3. 保持ポリシー（retention）

ローカルにどこまで残すかを選べる。

- **`window`（既定）**: 同期ウィンドウ内のみ保持。範囲外はローカルから整理。
- **`metadata_only`**: 範囲外も**メタデータ（ヘッダ・索引）は保持**し、本文/添付だけ削除して容量節約（検索ヒットは残る）。
- **`keep_all`**: 取得したものは消さない（容量優先でないユーザー向け）。
- 整理した本文/添付は**必要時に IMAP サーバーから再取得**（サーバーが源 → ローカルは可変キャッシュ）。

---

## 3.5 ローカル保存（取り込みは全部・保持は2軸）

**ステータス:** 実装済み（`feature/storage-tiers`）。

**方針としては全部取り込みを推奨**（メールクライアントとして最新が欠けるのは致命的なので、範囲は絞らない）。ただし `sync_window` 自体は**現状も有効**で、`imap_sync.rs` が値を読み、`'all'` 以外なら IMAP `SINCE` を適用して取得範囲を絞る（`account_set_sync_window` も生きたコマンド。UI からは隠す運用でよい）。既定は `'6m'`（COALESCE フォールバック）。初回のフル取得は安全上限あり。

**基本の考え方＝ローカルはキャッシュ。** 正本はサーバーにあり、ローカルの重いデータ（添付ファイル・全文本文）は**いつでも再取得できるキャッシュ**。**メタ情報と要約（`clean_body`）は恒久保存**（軽く、プロダクトの「記録性」に整合）。重いデータだけを2軸で出し入れする:

| 軸 | 設定 | 挙動 |
|---|---|---|
| **添付ファイル** | `full_window`「添付を手元に残す期間」 | ダウンロード済み添付を期間内は保持。**古いものは実ファイル削除**（メタは残り再DL可）。最終アクセスから**約3日は猶予**。既定 `all`（非破壊）。 |
| **本文（全文）** | `body_window`「テキスト全文を確実に残す期間」 | 期間内は全文を**保証保持**。より古い本文は**容量上限を超えたときだけ**古い順で**要約**（`clean_body` だけ残し `body_html_z`/`body_plain` を破棄。全文はサーバー再取得＝メール本文の 🔄）。**新規行の DB 既定は `off`**（0011 の DEFAULT 'off'、COALESCE も 'off'）。既存アカウントは 0012 で `off`→`all` に移行済み。 |

- **スター付きは常に保護**（添付・本文とも）。
- **添付はオンデマンド**（同期はメタだけ保存。本体は「開く／ダウンロード」時に初めてローカル保存）。
- **容量オーバー時の段階**: 上限まで全文 → 超えたら古い本文を要約（要約は極小なので 5% の余白＝1GB なら約50MB で数万通分を吸収）。**それでも保証データ自体が上限+5% を超える**ときは、要約では吸収できないので設定 UI で**上限値を赤字警告**（上限を上げるか保持期間を短くする）。
- **古いメールのローカル削除（キャッシュ追い出し）は採用しない**: 要約＋メタは軽く恒久保存する方が「手元に恒久的に残る証跡（記録性）」に合う。重いデータだけをキャッシュとして管理する。

> 境界は**時系列（新しい→古い）**に沿うので、新着が増えても境界が過去へずれるだけでブレない。

## 3.6 取り込みの進め方（全件メタデータ索引・バックグラウンド・再開可能）

**ステータス:** 計画（未実装。現状は `SAFETY_MAX=2000`＋前方向のみで「全部取り込み」に未達）。

§3.5「全部取り込み」を実現するための取得手順。**メタデータは全件・恒久**、本文/添付はキャッシュ。

- **全件メタデータ索引**：全フォルダの全 UID を `ENVELOPE`＋スレッド用ヘッダ（`REFERENCES` 等）だけ取得して upsert（**本文は落とさない＝軽い**）。範囲は絞らない。これで一覧に**サーバの全メールが出る**。
- **優先順位**：① 新着（増分同期）を最優先 → ② 古いメタデータは**低優先でバックグラウンド**に少しずつ。**古い分は急がない**。
- **再開可能**：フォルダ別に索引カーソル（どこまで遡ったか）を永続化。**アプリ終了・オフラインを跨いでも、次回起動時に DB を参照して続きから**バックグラウンド継続。
- **本文/添付**：メタが揃った後、本文は容量予算内で新しい順に取得（超過分は未取得＝開いた時にオンデマンド）。添付は従来どおり遅延。
- **チャンク＋中断可**：1,000 件程度ずつ FETCH、進捗発火、キャンセル対応。増分同期を止めないよう接続は分離/直列化。
- **非破壊**：行・メタは消さない（§3.5）。

### 進捗表示
- **左下カウント**：「ローカル索引済み / サーバ総数」を常設表示（例 `12,340 / 25,026`）。サーバ総数は同期時の `mailbox.exists` を保存して使う。＝手元ミラーの完成度ゲージ。
- **右下インジケータ**（既存）：実行中のフォルダ別 `current/total`＋中断。

## 5. 同期の流れ

```
毎回: Pass 0 = 破棄済み下書きのサーバー側後片付け（取り込みより先に実行）
初回: 新着を取得しつつ、全件メタデータ索引をバックグラウンドで開始（§3.6）
以降: 差分同期（UIDVALIDITY / UIDNEXT）で新着＋古いメタの索引を DB カーソルから継続
随時: 本文/添付はオンデマンド、重いデータは保持ポリシー(§3.5)でキャッシュ管理
```

> **Pass 0（破棄済み下書きの後片付け）**: 送信・破棄でローカルから消した下書きは、サーバー
> Drafts のコピー削除が失敗していることがある。取り込み（Pass 1）より**先に**墓標
> （`deleted_keys.remote_pending=1`）を見てサーバー側の削除を再試行し、消えていない下書きが
> 同じ同期で復活するのを防ぐ。墓標のあるキーは `insert_email` 側でも取り込まない。
> 詳細は [COMPOSE.md](COMPOSE.md) §1。

## 6. データモデル（accounts に設定列を追加）

詳細は [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md)。

- `accounts.sync_window`           — 取り込み範囲 `'1m'|'3m'|'6m'|'1y'|'2y'|'all'`。`imap_sync.rs` が読み、`'all'` 以外は IMAP `SINCE` で絞る（**現状も有効**。COALESCE 既定 `'6m'`。UI からは隠す運用でよい）【実装済み】
- `accounts.full_window`           — 添付を手元に残す期間 `'7d'|'30d'|'3m'|'6m'|'1y'|'all'`（既定 `'all'`＝非破壊）【実装済み】
- `accounts.body_window`           — テキスト全文を確実に残す期間（保証）`'3m'|'6m'|'1y'|'2y'|'all'`（新規行の DB 既定 `'off'`。既存は 0012 で `'all'` へ移行）。これより古い本文は容量超過時に要約【実装済み】
- `accounts.storage_limit`         — ローカル容量上限（バイト。既定 2GB。超過で古い本文を要約。+5% 超で赤字警告）【実装済み】
- `emails.body_compacted`          — 本文を要約保存に落とした印（`clean_body` のみ残存）【実装済み】
- `folder_sync.server_total`       — **サーバ側の総数**（IMAP `SELECT` の `EXISTS`＝サーバ由来）。左下「ローカル/サーバ」表示用【計画・0038】
- `folder_sync.index_cursor`       — 全件メタ索引の到達点（どこまで古い UID を索引したか）。再開に使う【計画・0038】
- `emails.body_state`              — 本文の状態 `absent`（未取得）/`present`/`evicted`（要約）。`body_compacted` を包含【計画・0038】
- `accounts.body_fetch` / `attachment_fetch` / `retention` — 旧モデルの列（現在は未使用。将来整理）

## 8. 削除・ゴミ箱のサーバー反映

削除は**2段階**。取り消しやすさ（手元の証跡）と、サーバーの整理を両立する。

| 操作 | ローカル | サーバー（IMAP） |
|---|---|---|
| **削除**（既定） | `folder='trash'` へ移動（`prev_folder`・`trashed_at` を記録。復元可） | **触れない**（元フォルダに残す） |
| **ゴミ箱を空にする** / **個別の完全削除** | 行を完全削除 | **Trash へ移動→完全削除**（best-effort・背景） |
| **迷惑フォルダを空にする** | 同上 | 同上（元は INBOX か Junk） |
| **保持期限切れの自動 purge** | 行を完全削除 | 触れない（自動削除でサーバーを消さない） |

- **サーバー反映の中身**（[`imap_sync::purge_emails_remote`](../src-tauri/src/services/imap_sync.rs)）: 元フォルダ（`prev_folder`／`folder`→サーバー名へ解決）で該当メールを **Message-ID 検索**し、Trash（`\Junk` ではなく `\Trash`）へ `UID COPY` → 元で `\Deleted`＋`EXPUNGE`（＝移動）→ 最後に Trash 側でも `\Deleted`＋`EXPUNGE`（＝恒久削除）。Trash が無いサーバーは元フォルダで直接 `EXPUNGE`。
- **best-effort・非ブロッキング**: ローカルは即削除して UI を返し、サーバー削除はアカウントごとにバックグラウンド実行。失敗しても警告ログのみ（ローカルは既に反映済み）。UID は uid_validity 変化に弱いので **Message-ID で解決**する（下書き削除と同じ作法）。
- **なぜ必要か**: 「空にする」でローカル行だけ消すと、サーバーの元コピーが残り、**全再同期やアカウント再登録で受信箱へ再ダウンロードされて復活**し得る。サーバーも消すことでこれを断つ。
