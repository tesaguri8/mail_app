# スレッド再構築エンジン（引用解析・論理スレッド）

**ステータス:** コア実装済み（v1）。**引用/署名分離・(from+時刻)抽出・fingerprint**（`services/quotes.rs`）、
**ヘッダ束ね＋ルートキー方式の論理スレッド割当**（`services/store/threads.rs`）、**会話ビュー（自分=右/相手=左の時系列バブル）**
（`components/Conversation.tsx`）、**手動の分割/再件名**、**返信送信時の References チェーン**まで実装。
自動分割は「控えめ＋手動主体」の方針（同件名でも別内容なら手動で切り出す）。**結合（merge）UI は後続**（コマンド `thread_merge` は実装済み）。
**位置づけ:** 「チャット形式メール表示」を単なる見た目でなく、**独自のスレッド再構築**まで踏み込む目玉機能。
**解決したい課題:**
1. 「**返信**」で過去メールを再利用し、**件名は同じ（`Re: …`）なのに中身が全く別**のメールが増えている → 標準のスレッド表示が誤って同じ束にまとめる。
2. **返信の引用が長くてイライラ** → 読みたいのは「新しく書かれた部分」だけ。

関連: [FEATURE_SPEC.md](FEATURE_SPEC.md) / [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) / [UI_UX_DESIGN.md](UI_UX_DESIGN.md)

## 0. 設計思想（普通のメール＋アプリ内ローカル再構成）

このエンジンは**普通のメールクライアントの上に乗る“表示の賢さ”**であり、メールの仕組みを変えない。

- **送信は標準RFCメール**。引用もそのまま引き連れて返信する。他クライアントと完全に整合（あくまで普通のメール）。
  - **送信時に引用を除去しない**: 相手が引用履歴を必要とする場合があるため。こちらの好みを相手に強制しない。
  - **重複引用の不快さは“自分の表示側だけ”で解消**する（送信物は普通のまま）。これが本アプリの核心的な分担＝開発動機。
- **追加するのは新フィールドだけ**（例 `X-Protected-Regions`）。**他クライアントは無視するだけ**（後方互換）。
- **ID は端末ローカル・アプリ内のみ**で割り振る（**中央管理しない**）。保存済みメールデータ内で完結。**端末間で ID が一致する必要はない**（各端末が自分の保存分から独立に表示を再構成）。
- **照合の鍵は標準ヘッダ**（`Message-ID` / `In-Reply-To` / `References`）＋引用属性。これは“中央管理”ではなく**メール自身が持つ標準ID**を使うだけ。
- **生メールは丸ごと保持**（普通の引用返信・下記フォールバックのため）。**表示だけ賢く**する。
- **引用の二重保持を避ける（表示の重複排除）**: 受信した返信の引用部分は、たいてい**すでに別メッセージとして保存済み** → 会話表示では**新規部分（`clean_body`）だけ**を見せ、履歴は保存済みメッセージで再構成。
  - **保存済みの履歴が無い場合**（後からCC・別経路で開始したスレッド等）は、引用部分を**畳んだフォールバック**として表示（引用が唯一の履歴になるため捨てない）。

> 要約: **生メールは普通に保存 → 表示は「新規部分＋保存済みから再構成」 → ID は端末ローカル → 送信は普通＋追加フィールドのみ。**

## 1. なぜ標準のスレッド分けが破綻するか

メールの返信には親メッセージを指すヘッダが付く:

- `Message-ID`: 各メール固有のID
- `In-Reply-To`: 返信元の Message-ID
- `References`: スレッドの Message-ID 連鎖

一般的なメールソフトは `In-Reply-To` / `References` ＋件名でスレッドを組む。
ところが「**内容は別件なのに古いメールに返信**」されると、ヘッダは古いスレッドを指したまま・件名も `Re: 同じ件名` のまま → **誤って同じスレッドに合流**してしまう。

→ ヘッダ依存が破綻するこの場面こそ、本エンジンが狙う領域。**中身（引用）を見て分ける／繋ぐ**。

## 2. 連結判定（現状: ヘッダ union-find）

**現状の実装は「標準ヘッダによる確定的な束ね（union-find）」**（`services/store/threads.rs`）。
`Message-ID` / `In-Reply-To` / `References` からルートキーを決め、同じルートを持つメールを同じ論理スレッドに束ねる。
引用シグナル（優先2・3）は**抽出・保存はしているが、まだスレッド連結には使っていない**（下表の「状態」を参照）。

| 優先 | シグナル | 役割 | 状態 |
|---|---|---|---|
| 1 | `Message-ID` / `In-Reply-To` / `References` | 各メールの確定ID。ルートキーで束ねる（union-find） | **実装済み** |
| 1' | `Thread-Index` / `Thread-Topic`（Outlook/Exchange） | 会話ツリーをエンコードした独自ヘッダ。`References` 欠落時の補完候補 | 抽出・保存のみ（束ねには未使用。§7.5 D／§8） |
| 2 | **引用属性行の (from + 送信時刻)** | ヘッダが当てにならない時の連結／分割の手がかり（構想）／**手元に無いメールの引用を見つける** | `quoted_from`/`quoted_at` を抽出し、**手元のメールと照合して `matched_email_id` に記録**（下記）。**連結には未使用** |
| 3 | **引用本文のフィンガープリント**（正規化ハッシュ） | 同じ履歴を引いているかを照合（構想） | `fingerprint` として抽出・保存のみ（連結には未使用） |
| 4 | 件名の正規化（`Re:` `Fwd:` `RE：` `転送` 除去）＋相手（counterparty） | **ID ヘッダが全く無い場合のみ**のフォールバック | **実装済み**（`derive_root_key`） |

> 注: 現状は ID ヘッダが揃っていればそれで束ね、揃わない時だけ「正規化件名＋相手」でフォールバックする。
> 引用属性・fingerprint を使った「返信で別件」の自動分割は**将来拡張**（構想）で、現状は content 由来の自動連結・分割は行わない。

### 返信の手がかり（`thread_hints`・2026-10-20）

**自分の送信メールの控えに Message-ID が無いと、ヘッダだけでは返信を親へつなげない。**
0.1.0-alpha.34 までの送信は Message-ID を付けていなかった（lettre の `build()` は Date しか補わない。
中継が後から付けた ID は Sent の控えに入らない）。その控えへ返信すると In-Reply-To を付けられず、
親が新規のメールなら References も空になって、返信は新しいスレッドになっていた（vaio の実例: 53057 への全員返信）。

- 送信は毎回 Message-ID を自前で採番する（[COMPOSE.md](COMPOSE.md) §1）。**これからの控えには ID が入る**
- 既にある ID の無い控えへの返信は、`reply_to_email_id`（返信元の emails.id）から組む
  （`services/store/reply_threads.rs`）:
  - References は親の References＋親の In-Reply-To（In-Reply-To は付けない）
  - 送信のときに `thread_hints`（0067: 返信の Message-ID → 親の行の `canonical_key`）を残す
- 割当（取り込み時の `compute_root_key`）は手がかりを最初に見て、親の `thread_id` を継承する。
  再構築（`rebuild_threads_conn`）は手がかりで返信と親を union-find で結ぶ。親はヘッダを持たないが、
  結んだ親は件名のフォールバックではなく束ねたキーで割り当てる
- **相手のメーラーには親が分からない**（ヘッダに親の ID が無い）。直るのは、これから送る控えから

### 引用属性行に (from + 時刻) が埋まっている

返信メールの引用部分の冒頭には、引用元の差出人・時刻が含まれることが多い:

```
On Mon, 30 Jun 2026 10:00:00 +0900, 山田太郎 <yamada@example.com> wrote:
2026年6月30日(月) 10:00 佐藤 <sato@example.com>:
-----Original Message-----
差出人: 山田太郎 <yamada@example.com>
送信日時: 2026年6月30日 10:00
```

この属性行から **(quoted_from, quoted_at)** を抽出し、手元の実メッセージの `From` ＋ `Date` と
**許容幅つきで突合**すれば、引用ブロック ↔ 元メッセージを結べる。
→ 「アドレス＋時間でIDを振る」発想は、この**引用突合の照合キー**として効く。

### 引用ブロックの分け方と照合（実装済み・2026-10-11）

**きっかけ（実データ 2026-10-03）**: Outlook の返信の下に `-----Original Message-----` で前のメールが 2 通
連なっていた。**2 通とも受信箱に無く、利用者が初めて読む内容**だったのに、引用として「引用を表示」に
畳まれて見落とした。差出人・日時も取れていなかった（`quoted_from` / `quoted_at` が NULL）。

- **1 通ずつに分ける**（`services/quotes/blocks.rs` の `quote_blocks`）: 引用の領域を、`>` の付かない
  「元のメッセージ」の区切り（`-----Original Message-----` / `-----元のメッセージ-----` /
  `---------- Forwarded message ---------` / `--- 引用元メッセージ ---` / `--- 転送されたメール ---` / Apple の `Begin forwarded message:`。
  終わりの印の `--- Original Message Ends ---` は区切りにしない。判定は `header::is_separator_text` の 1 か所）、
  **次に見出しが来る罫線**（Outlook の下線 `________________` の次の行が `From:` 等。下記）か、区切りの無い見出し（`From:` の後の数行に
  `Sent:` / `Date:` / `送信日時:` / `日付:`）、**引用の途中の属性行**（`On … wrote:` / `〜さんは書きました:` 等）で切る。
  **`>` の中の見出しでは切らない**（引用の中の引用は外側の 1 通の一部）。字下げした区切り（Thunderbird の
  `On … wrote:` の下に字下げで続く転送）でも切り、そのブロックの本文は共通の字下げを外して左に寄せる。
  `block_order` は新しい順（0 が直前の 1 通）。
  - **属性行の書き方**: `On … wrote:`（全角コロンの `wrote：` も）/ `〜さんは書きました:` / `<名前> <addr> のメール:`
    （iPhone などの日付が先の `2026/10/20 11:21、名前 <addr> のメール:` は、**行頭の日時も読む**ので、手元に無ければ 1 通の枠になる）/ Apple Mail の `…, 名前 <addr>:` /
    中国語の `… 写道：`・フランス語の `… a écrit :`（**アドレスを含む行だけ**）。`<名前> … より` は本文の一文と
    見分けにくいので読まない（2026-10-20 時点）。
  - **属性行の日時も読む**（2026-10-20・v6）: 差出人と日時がそろわない引用は、照合も枠もできず見えなくなる
    （vaio で 12,849 行のうち 5,209 行。うち 3,745 行は差出人だけ読めて日時が無かった）。日時が先で差出人が続く形は、
    日時として読める（`when::parse_quoted_time`）位置で分けて両方を取る:
    日時と差出人を読点・カンマで区切る Apple Mail の `Sep 9, 2026, 9:09 AM +0900, 名前 <addr>:` と iPhone の
    `2026/10/02 12:10、名前 <addr>のメール:`（区切りの前後の空白・`,`・名前の無い形も）、時刻の後に空白で差出人が続く
    Gmail 日本語版の `2026年10月2日(金) 17:55 名前 <addr>:`・`2026年10月2日 17:55:00 addr：`・`2026/10/2 12:10:00 に addr 名前:`、
    中国語の `在 2026-10-02 12:10:00，"名前" <addr> 写道：`・`名前 <addr> 于2026年10月20日周二 11:21写道：`。
    **差出人にアドレスがあるときだけ**（本文の「2026年10月2日(金) 17:55 に伺います。」では取らない）。
    日時が読めない形は、これまでどおり差出人だけ。
  - **v7 で読むようにした形**（2026-10-20。v6 の後も vaio で 1,613 行が読めなかった）:
    - **改行で 2 行に割れた属性行**（`Oct 2, 2026, 9:05 PM +0900, 名前` の次の行が `<addr>:` / `…、名前 <` の次の行が
      `addr>:` / `<addr>のメール:`）は、前の行とつないで読む（`attribution::wrapped_attribution`）。つないだほうが
      多く読める（日時が取れる・1 行では属性行と分からない）ときだけ。引用の途中の 1 通でも同じ。
    - Android 版 Gmail の `火, 20 10月 2026、11:21 名前 <addr>:`。**曜日から始まる**この形だけは、アドレスが無くても
      名前を差出人として読む。曜日の `(月)` / `月曜日` を月の印と取り違えていたのも直した（`when.rs`）。
    - **アドレスも続く見出しも無い `送信者：名前` / `From: 名前`** は、通知メールの本文のことが多いので切らない
      （`header::from_line_backed`。続く 4 行までに別の見出しがあれば、これまでどおり引用の始まり）。
    - ほかに確かめた形（試験 `quotes/tests/forms.rs`）: アドレスに mailto が入れ子の `From: 名前 <a@b<mailto:a@b>>`、
      CSS の行の後の `----- 引用元メッセージ -----`、名前に空白・和文が混じる `On … wrote:`、`に` の無い
      `2026/10/02 12:10:00 名前 addr 名前:`、`Begin forwarded message:`、名前の無い Apple の `…, addr:`。
  - **罫線**（v7）: 罫線だけの行（`____` / `=====` / `-----` / `━━━` / `****`。5 字以上）は、メールマガジンの飾りや
    署名にも使われるので、**それだけでは区切りにしない**。罫線の次の空でない行（罫線は飛ばす。4 行まで）が
    見出し（`From:` / `差出人:` / `Date:` 等）か区切りの文字（`Begin forwarded message:` 等）のときだけ区切りとみなす
    （`header::starts_rule_separator`）。v6 までは 16 本以上の `_` を常に区切りとしていたので、メールマガジンの
    `____…☆☆` の後ろが差出人も日時も無い引用として隠れていた。
  - **途中の属性行**は、その行から差出人・日時を取る（見出しが続けば見出しを優先）。本文の
    「…と彼は書きました:」「On Monday, I wrote:」で切らないよう、**日付（4 桁の数字）かアドレス（`@`）を含む行だけ**を属性行とみなす。
  - **きっかけ（実データ 2026-10-09）**: 転送（`-------- Forwarded Message --------`）の下に、太字の Outlook 見出し
    （`*From:*` / `*Sent:*`）・`On 2026/10/05 6:28, 名前wrote:`・字下げした Gmail 転送と `-----Original Message-----`
    が 7 通重なっていたのに、最初の区切りで 1 か所しか切れず、残りが 1 つの枠に入っていた。
  - **次の 1 通の始まりは、いまの 1 通の見出しより後ろでだけ探す**（項目名と値が別の行にある見出しでは、
    `From:` の後に `To:` 等が続き、区切りの無い見出しと見分けられないため）。
  - **予備の判定: 見出しが近くに固まっていれば区切る**（2026-10-20 利用者の発案。`quotes/header/cluster.rs` の `starts_header_cluster`）。
    既知の形をすべて並べる代わりに、**既知の形の判定で区切れなかった行だけ**を見る。空行を除いた 12 行の中に、
    差出人（`From` / `差出人` / `送信者`）・日付（`Date` / `Sent` / `日付` / `送信日時`）・宛先（`To` / `宛先`）・
    件名（`Subject` / `件名`）・`Cc` の見出しが **3 種類以上**あり、そのうちに**差出人と日付**があり、値に
    **アドレス（`@`）と日時として読めるもの**が 1 つ以上あれば、その最初の見出しの行から 1 通とする。
    値は同じ行でも、空行を挟んだ次の行でもよい。**To と Subject は必須にしない**（Bcc で受けたメール・
    `On … wrote:` の形には無い）。本文の申込書や見積の「件名:」「日付:」「宛先:」だけの段落は、差出人が無いので区切らない。
    - **残る誤検出**: 本文に「差出人:」と、近くに日時の読める「日付:」が並ぶと、予備の判定ではなく既知の形
      （区切りの無い Outlook の見出し＝`From:` の後の数行に日時の項目）で区切られる。アドレスの無い Outlook の
      見出し（`From: 山田 花子`）を読むために、ここではアドレスを求めていない。区切っても中身は枠に残る（下）。
- **見出しを読む**（`services/quotes/header.rs`）: 区切りの次から空行までの `Key: value` を読む。
  差出人＝`From` / `差出人` / `送信者` / `送信元`、日時＝`Sent` / `Date` / `送信日時` / `日付` / `日時`、
  件名＝`Subject` / `件名`（中国語の `发件人` / `寄件者`・`时间`・`主题` / `主旨`・`收件人` / `收件者` も）。
  **項目名の全角英字は半角にそろえて照らす**（`ＣＣ` / `Ｃｃ`）。古い日本語版 Outlook の **`送信:` は値が日時として読めるときだけ**日時とする
  （本文の「送信: ○○」で誤らないため）。**見出しの順番には頼らない**（`Subject → Date → From → To` /
  `差出人 → 件名 → 日付 → 宛先` 等も読む。本文の始まりを `From:` で切ったときは、その上に続く見出しも含める）。
  `To` / `Cc` は読み飛ばし、折り返した宛先の行も見出しの一部として飛ばす。
  **項目名と値が別の行にある書式も読む**（Thunderbird が HTML の表を文字にした形。最初の項目の値が空で、
  空行を挟んだ次の行が項目でなければ、その行を値とし、空行の先に次の項目が続く間は見出しとして読み続ける）。
  区切りは `-------- Forwarded Message --------` / `-------- Original Message --------` /
  `-------- 転送メッセージ --------`、項目は `Subject` / `Date` / `From` / `To`（日本語版は `件名` / `日付` / `差出人` / `宛先`）。
  普通の見出しで件名だけ空のとき（`Subject:` の後が空行と本文）は、本文の 1 行目を件名にしない。
  見出しの途中の知らない項目（`Message-ID:` / `場所:` 等）は、読み取りを止めずに飛ばす（表の形では値の行ごと）。
  **各行の間に空行が入る見出しも読む**（2026-10-20・v9。HTML を文字にしたときの 2 重改行で、`差出人:` `日付:` `宛先:` …
  が 1 行おきに並ぶ。英語の Outlook の、行頭に空白の付いた `From:` / `Sent:` も同じ）。空行の先が**まだ読んでいない種類の項目**
  なら見出しとして読み続け、本文の行が来たら止まる。同じ種類（2 通目の `差出人:`）が来たら、そこは次の 1 通として止まる。
  v8 までは最初の空行で止まり、差出人だけ取れて日時が NULL になっていた（vaio の 1 通で 18 枠のうち 7 枠）。
  **HTML の太字が text/plain に残った `*From:*` / `*Sent:*` も読む**（項目名の前後と値の先頭の `*` を外す）。
  項目名の読み取りは `header_field` の 1 か所で、区切りの無い見出しの裏付け（日時の項目）もこれを使う。
  - **きっかけ（実データ 2026-10-20）**: 転送が 12 通入れ子になったメールで、Thunderbird の形の 3 通が
    差出人・日時を読めずに枠にならず、画面のどこにも出ていなかった（うち 1 通に利用者の要るダウンロードの URL）。
- **日時を読む**（`services/quotes/when.rs`）: 書式を当てるのではなく、年・月・日・時刻・午前午後・時差の字句を拾う。
  `Friday, October 2, 2026 5:55 PM` / `2026年10月2日(金) 17:55` / `2026/10/02 17:55` / `Fri, 2 Oct 2026 17:55:00 +0900`
  / `Fri, Oct 2, 2026 at 5:55 PM` / `2026年10月2日 午後5:55` を読む。**数字だけの日付は「年が先」のときだけ**
  （`10/02/2026` は月日の順が決まらないので読まない）。
- **照合する**（`services/store/quote_match.rs`）: 差出人（**アドレス、または名前**。Outlook は社内宛てで
  アドレスを省き名前だけにすることがある）と日時が合う手元のメールを探す。**許容幅は ±2 分**（Outlook の
  `Sent:` は秒を落とす）。**時差が書かれていない**日時（Outlook の `Sent:` / 日本語の `送信日時:`）は、
  前後 14 時間の幅で候補を引き、**候補の送信者の時刻**（`emails.date` の時差）どうしで比べる。
  時差が書かれていれば UTC で比べる。下書きと自分自身は除く。複数あれば時刻の近いもの。
  - 取り込みの直後（`insert_email`）と、ローカル再解析（`reprocess_all`）のあとに `matched_email_id` を入れる。
  - 日時だけの範囲で引くための索引 `idx_emails_date_ts`（0065）。

## 3. ID とグラフモデル（「スレッド＝IDの集合」）

```
各メール        = ノード（Message-ID ＋ from/to/sent/subject）
ヘッダ参照       = In-Reply-To / References のエッジ（header由来）※現状の連結はこれのみ
引用ブロック     = 「どの過去メッセージを引いているか」のエッジ（content由来）※抽出のみ・連結には未使用
   ↓
エッジで繋がる連結成分（union-find）＝ アプリ独自の「論理スレッド」
```

- **論理スレッドはヘッダ由来のルートキーで union-find 束ね**する（`References` 先頭 → `In-Reply-To` → 自分の `Message-ID`）。
  - ID ヘッダが**全く無い場合のみ**、「正規化件名＋相手（counterparty）」でフォールバックして束ねる。
  - 引用チェーン由来の分割・結合（件名同じでも引用が無関係なら分ける等）は**将来拡張**（構想）。現状は content 由来の自動連結・分割は行わない。
- 各メールは 1 つの論理スレッドに所属（`emails.logical_thread_id`）。割り当ては `auto` / `manual` を区別。

---

## 4. 分割・結合ポリシー（自動束ね＋手動分割/結合）

- **自動はヘッダによる束ねのみ**: ルートキー（Message-ID/In-Reply-To/References）による union-find で論理スレッドを構築する（§2・§3）。
  - **content 由来の自動分割（件名同じでも引用が無関係なら分ける等）は行わない**（＝「控えめ＋手動主体」）。引用シグナルは保存済みだが連結・分割には未使用。
- **分割・結合はユーザーの手動操作**:
  - 「このメールを別スレッドに分ける」（`thread_split`）／「このスレッドと結合する」（`thread_merge`）を手動で行う。
  - `thread_assignment = 'manual'` のメールは再計算で動かさない（ユーザー意思を尊重）。
  - 手動操作は将来の判定改善のための材料にもする。
- **将来拡張**: 引用属性・fingerprint を使った自動分割候補の提示（確信度つきで「別件かも」を控えめに示す）は構想段階。

## 4.5 アプリ内での再件名・整理

受信したメールの**元の件名はそのまま保持**しつつ、論理スレッドに**アプリ独自のタイトル**を付け直せる。

- **再件名（リネーム）**: 「`Re: 例の件` を `A社／6月見積もり` に」のように、スレッドへ分かりやすい題名を付与（`logical_threads.title`）。元の `Subject` は `auto_title` として残す。
- **同件名・別内容の整理**: 手動分割した各論理スレッドに別々のタイトルを付ければ、「件名は同じでも別案件」を**一覧上で明確に区別**できる。
- **ラベル/タグ**: 既存のタグ機能（[FEATURE_SPEC.md](FEATURE_SPEC.md) §2.3）と連携し、論理スレッド単位で分類。
- **手動の分割/結合**（§4）と合わせ、受信トレイを「自分が分かる単位」に組み替えられる。
- リネーム・分割・結合は `manual` 扱いとして保持し、再解析で勝手に戻さない。

> ねらい: メール提供元の件名付けに振り回されず、**アプリ内で自分の整理体系に作り替える**。これが「整理しやすさ」の核。

## 5. 表示（引用イライラの解消・SNS 風）

- 取り込み時に**引用・署名を解析して剥がし**、各メールの「**新しく書かれた部分（clean_body）**」を生成。
- チャットのバブルは clean_body のみを表示（自分＝右／相手＝左、時刻順）。
- 引用は**折りたたみ**、「引用を表示」で必要時のみ展開。
- **手元に無いメールの引用は畳まない**（2026-10-11）: 引用ブロックのうち、**差出人と日時の両方が読めて**、
  手元のメールと照合して見つからず、**同じ会話のどのメールの新規部分も含まない**ものは、
  親のバブルの**上**に **1 通ずつ小さなバブル**で出す（封筒のアイコンと差出人・日時・件名の見出し。
  `components/UnseenQuotes.tsx`）。
  - **見た目**（2026-10-14 利用者の要望で改めた。「黄色は逆にメインに見えてしまう」）: 地の色・文字の色は
    ふつうのバブルと同じにし、**枠線だけ点線**にして「手元に届いたメールではない」ことを示す。1 枠ずつの
    「このメールに含まれていた、未受信のメール」は外し、封筒のアイコンのツールチップ（title・aria-label）に移した。
    **並びと置き場所**（2026-10-20 利用者の判断・案 A）: 枠は**古い順**（`date` の昇順）に並べ、**親のバブルの上**に置く。
    本文の中では新しい順（転送の外側 → 内側）に出てくるので、下に並べると会話のその部分だけ時間が逆に進み、
    日付のつまみも逆向きになっていた。上に古い順で置くと、会話全体が上から下へ時間どおりになる
    （`UnseenQuotes.tsx` の `oldestFirst`）。**日時の読めない枠**は、本文で直前の枠（その続きとして枠になったもの）の
    すぐ上（古い側）に置く。本文の先頭で直前が無ければ、直後の枠のすぐ下に置く。
    どのバブルのものかは、見出しの下向きの矢印と「下のメールに引用されていた」の文言、まとまりの横の点線
    （バブルの寄せる側。まとまりの下端まで）で示す。バブルの id とつまみの目印は枠を含めず**バブル本体**に付ける
    （最新のバブルへの初期スクロール・全文の開閉の位置合わせが、枠ではなくバブルに合う）。
    枠の並びのいちばん上に一度だけ、小さく「↓ 下のメールに引用されていたメール N 通（未受信）」を出す（1 通でも出す。
    点線の意味を言葉で一度だけ添える役目で、1 通のときも邪魔にならなかった）。
  - 枠は日付のつまみにも 1 件ずつ載る（[CONVERSATION_TIMELINE.md](CONVERSATION_TIMELINE.md) §2.3）。
  手元にある引用は、いままでどおり「引用を表示」に畳む。
  - **差出人・日時の分からない引用（`…が書きました:` 等）は 1 通の枠にしない**。手元にあるかを確かめられず、
    出すとほとんどの返信で親のメールを二重に見せてしまう。**ただし黙って捨てない**（2026-10-20）:
    直前の引用を枠として出していれば、その枠の続きとして見出しごと残す（読めない見出しの転送の中身が
    画面から消えないように）。直前の 1 通が手元にある（または最初の引用）ときは、そのメールの側か
    「引用を表示」で読めるので、いままでどおり畳む。
  - **会話ビューを開くたびに、保存済みの本文から分け直して照合する**（`ThreadMessage.unseen_quotes`）。
    **再解析していない既存のメールにも効き**、元のメールが後から届けば次に開いたときから畳まれる。
  - 枠の本文の URL は、ふつうのバブルと同じ `AutoLinkText` でリンクにする（2026-10-20 に試験で固定）。
  - **見出しの日時はふつうのバブルと同じ表記で出す**（2026-10-20。`utils/datetime.ts` の `formatQuotedDateTime`）。
    見出しのままの文字列（`at`）では `Tue, 20 Oct 2026 11:21:08 +0900` / `Tuesday, October 20, 2026 11:36 AM` /
    `2026/10/02 12:10` が混ざるので、読んだ日時（`date`）から作り、元の文字列はツールチップに残す。
    **時差が書かれていれば端末の時刻に直し、書かれていなければ書かれたままの時刻で出す**。どちらかは `date` の
    末尾の時差の有無で分かる（`QuotedTime::to_iso` は時差の無いものに付けない）。読めなければ `at` をそのまま出す。
  - **添付は外側のメールのもの**なので、枠には出さず外側のバブルのクリップに出す。本文に埋め込んだ転送では、
    どの添付がどの枠のものかを確実に分ける手がかりがヘッダに無い（Outlook・Gmail・Thunderbird の転送の見出しは
    添付を書かない）ので、振り分けない（2026-10-20）。
  - **転送メールが message/rfc822（.eml）で付いている形は、枠にならない**（本文に入っていないので）。
    全文表示の添付の一覧で .eml の行の「中の添付を見る」から、中の添付を 1 件ずつ開く・保存できる
    （`services/eml_parts.rs`・`components/EmlInnerAttachments.tsx`。2026-10-20）。.eml を取得したあとで
    その場で解析し、中の添付は `attachments/<添付id>/inner/<序数>/` に書き出す（追い出しで一緒に消える）。

```
┌ 見積もりの件（論理スレ A）
│  相手 ▏ 来週の打ち合わせ可能ですか？
│  自分 ▕ 火曜の午後はいかがでしょう
└
┌ 見積もりの件（論理スレ B＝同じ件名・別内容）   ← 引用が別履歴なので手動で分割
│  相手 ▏ 別件ですが請求書の宛名を…
└
```

- **同じ Message-ID の写しは 1 つのバブルにまとめる**（2026-10-20）: 自分宛の送信は、受信箱と送信済みに
  同じ ID の写しが 2 通ある。会話では受信箱の写し（未読・既読の操作と「本物の自分から」の印を持つ）を残し、
  並びは先に出た写しの位置を保つ（`threads.rs` の `collapse_copies`）。ID の無い行はまとめない。
  一覧・検索の件数バッジも同じ基準で数える（`emails.rs` の `COPY_KEY`）。
- 横断検索（FTS5）は **clean_body** に張ると、引用の重複ヒットが消えて精度が上がる。

## 6. 解析パイプライン

```
受信(IMAP) → MIME解析(mail-parser)
   → 本文正規化（HTML→テキスト, 改行・空白正規化）
   → 引用/署名の分離（clean_body と quotes[] を抽出）
   → 各 quote から (quoted_from, quoted_at, fingerprint) を抽出（連なった「元のメッセージ」は 1 通ずつ）
   → 手元のメールと (from, 時刻) で照合して matched_email_id を記録（連結には未使用）
   → 連結判定（現状: ヘッダのルートキーで union-find。ID ヘッダが無い時のみ 件名正規化＋相手 でフォールバック）
   → 論理スレッド割当（auto。manual は固定）
   → DB 保存 ＋ FTS5(clean_body) インデックス
```

すべて**ローカルの Rust 側**（`src-tauri/src/services/parser.rs`＝MIME解析／`services/quotes.rs`＝引用・署名分離（属性行 `attribution`・署名 `signature`・1 通ずつの分け方 `blocks`・見出し `header`・差出人 `sender`・内容照合 `anchor`・日時 `when` を `services/quotes/` 配下に分けて置く）／`services/store/threads.rs`＝論理スレッド束ね。専用の `threading/` ディレクトリは無く、フラットなファイル構成）で完結。SNS 中継のようなクラウド依存は不要。

## 7. 引用・署名の分離（実装の本体・難所）

メールの引用形式は多様。ヒューリスティックを作り込む必要がある。

- **形式の多様性**: plain の `>` 引用、HTML の `<blockquote>`、インライン返信（行間差し込み）、トップ/ボトムポスト。
- **属性行の言語差**: 日本語（`〜さんは（書）きました`, `差出人:` `送信日時:`, `-----元のメッセージ-----`）／英語（`On … wrote:`, `From: … Sent: …`, `-----Original Message-----`）の**パターン辞書**を用意。
- **署名・定型句**: `-- ` 区切り、`Sent from my iPhone`, 会社署名ブロック等の除去。
- **参考にする考え方**: Mailgun **talon**、GitHub **email_reply_parser** の手法。Rust で移植・自作。
- **時刻のゆらぎ**: タイムゾーン差・秒丸め → 突合は許容幅（例: ±数分）で行う。

> **100% にはならない前提**。スコア＋確信度で扱い、誤りは手動上書きで救済する（§4）。

## 7.5 活用できるヘッダ・メタデータ

メールヘッダには件名/本文以外にも、スレッド化・仕分け・信頼判定・解析に使える情報が多くある。
標準（RFC 5322 / 各拡張）と、送信側システムが付ける独自 `X-*` の両方が存在する。

### A. スレッド化に直接効く
| ヘッダ | 用途 |
|---|---|
| `Message-ID` / `In-Reply-To` / `References` | 返信連鎖の確定的な連結（**実装済み**・現状の束ねの中核） |
| `Thread-Index` / `Thread-Topic`（Microsoft） | Outlook/Exchange が会話ツリーをエンコード。`References` 欠落時の補完候補。**現状は解析・保存のみ（`parser.rs` で `thread_index` を抽出）で、束ねには未使用** |

### B. 仕分け（自動分類）に効く
| ヘッダ | 用途 |
|---|---|
| `List-Id` / `List-Unsubscribe` / `List-Post` | **メルマガ・ML の判定**。個人メールと一括配信を分離（「仕分けが大変」の主因に効く） |
| `Precedence: bulk/list` / `Auto-Submitted: auto-*` | 自動送信・一括メールの検出（自動返信・通知の振り分け） |
| `X-Priority` / `Importance` | 重要度。ホーム/ウィジェットの強調に利用 |
| `Delivered-To` / `X-Original-To` | **自分のどのアドレス/エイリアス宛か** → マルチアカウント・用途別仕分け |
| `Return-Path` / `Sender` / `Reply-To` | 実際の送信元・返信先（なりすまし・転送の判別、返信先の最適化） |

### C. 信頼性・なりすまし検知
| ヘッダ | 用途 |
|---|---|
| `Authentication-Results` / `Received-SPF` / `DKIM-Signature` / `ARC-*` | SPF/DKIM/DMARC の認証結果。**差出人の正当性スコア**（「返信なりすまし」「別人化」の警告に有用） |
| `Received:`（経路チェーン） | 配送経路・原発時刻。発信元の推定 |

### D. 解析のヒント
| ヘッダ | 用途 |
|---|---|
| `X-Mailer` / `User-Agent` | 送信クライアント種別 → **引用/署名の形式推定**（例: iPhone Mail なら属性行パターンを切替）して §7 の解析精度を上げる |
| `Content-Type` / `Content-Language` | HTML/plain、本文言語 → 属性行パターン辞書（JP/EN）の選択 |

### E. 送信側システム独自の `X-*`（非標準・保証なし）
- CRM・問い合わせ管理・グループメール等が独自ヘッダを付けることがある（例: チケットID・キャンペーンID・配信元システム名など）。
- **存在すれば**案件IDとして強力な手がかりになるが、**送信側依存で保証されない**。あれば使う「ボーナス」として扱い、基盤は A〜D の標準ヘッダ＋引用解析に置く。

> 方針: 解析時にこれらを抽出して保存し、スレッド化（A・E）・自動仕分け（B）・信頼表示（C）・解析切替（D）に活用する。
> ただし**ヘッダ系は「返信で別件」に弱い**ため、最終的なスレッド分割は引用解析（§2 優先2・3）が上書きできる設計を保つ。

## 10. フェーズ上の位置づけ

コア機能の一部として段階的に実装（[DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md)）:
